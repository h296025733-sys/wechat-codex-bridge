# 微信 ↔ Codex 文字聊天桥

**把本机 Codex 接入微信文字聊天所需的安装、授权、配对和诊断，整理成可分享的工具包。**

连接失败时，经常不知道问题停在哪一层：Node 能不能联网、模型账号有没有授权、微信是不是已经绑定、网关是否真正 ready，还是消息到了但模型没有回答。把这些步骤混在一个安装脚本里，容易出现“进程启动了，所以都好了”的误判。

这个项目按独立阶段组织连接流程。接收者从模板生成自己的运行目录，使用自己的授权和微信绑定，启动本地服务，再用手机做真实收发与上下文检查。

仓库分享安装方法与脚本，不分享私人运行状态。Windows 有配套 PowerShell 入口；其他系统的适配方式保留在参考说明中。

## 连接路径与使用范围

```text
微信 ClawBot
  → 微信通道
  → 本机 OpenClaw
  → 当前使用者授权的 Codex
  → 文字回复返回微信
```

默认配置为文字聊天，工具被禁用，服务监听回环地址。电脑与网络需要持续可用，默认没有开机自启。

模型授权与微信扫码是两个独立步骤。使用同一个 ChatGPT 账号，也不意味着自动导入 Codex 桌面中的历史对话或记忆。项目使用使用者当前账户的可用权益与额度，没有配置 API Key 回退，也不承诺无限量使用。

## 为什么生成独立项目

`scripts/New-Bridge.ps1` 从 `assets/project/` 复制模板到一个空目录，不覆盖已有项目。生成前检查 Windows、Node.js 24+、npm 与端口；目标不能是磁盘根目录，非空目录需要按已有安装状态继续处理。

生成过程建立本项目自己的状态、日志、临时文件和运行目录，并随机生成本机网关授权值。它只生成项目，没有安装包、认证账号或发送微信消息。

这样可以把配置、端口与进程归属限定在当前项目中，避免为了新连接影响其他已经在运行的 OpenClaw 服务。

## 安装与验证分成六个阶段

| 阶段 | 入口 | 该阶段完成能说明什么 |
| --- | --- | --- |
| 项目生成 | `New-Bridge.ps1` | 独立目录和初始配置已建立 |
| 网络诊断 | `Detect-Network.ps1`、`Probe-Network.ps1` | 对应探测在当前网络下有结果 |
| 依赖安装 | `Install-Runtime.ps1` | 实际安装分支及所需依赖的状态 |
| 模型授权 | `Login-ChatGPT.ps1`、`Check-Auth.ps1` | 本项目可用授权与认证信息 |
| 微信配对 | `Pair-WeChat.ps1` | 微信通道绑定的实际结果 |
| 启动与收发 | `Start-Bridge.ps1`、手机验证 | 网关、模型和微信往返链路的分别结果 |

不能用前一阶段替代后一阶段。浏览器授权页显示成功，需要结合后台认证结果；网关 ready，需要再核对模型请求；真正完成微信连接，需要用户在手机上看见对应回复。

## 快速使用：让 Codex 按本机状态执行

推荐先将仓库下载到本机，再给自己的 Codex 明确任务：

```text
请读取这个仓库的 SKILL.md，将我自己的 Codex 接到我自己的微信。
使用独立目录，先检查网络、端口与已有安装。
需要我授权或扫码时告诉我。
完成后用手机进行两轮真实收发和上下文验证，说明每一层的实际结果。
```

技能文件是安装工作流说明。README 展示的是工具包结构，不代表本轮已经替使用者执行了真实安装。

如果手动生成 Windows 项目，模型名称应使用自己环境实际支持的 `openai/` 标识：

```powershell
$BridgeModel = Read-Host '输入当前账户支持的 openai/模型标识'
.\scripts\New-Bridge.ps1 -TargetDir 'D:\projects\wechat-bridge' -Model $BridgeModel -Port 18791
```

目录和端口是示例。生成后先阅读运行项目的 `USAGE.md`，再按对应脚本帮助与实际状态完成网络、安装、授权和配对步骤。

## 网络诊断与进程归属

浏览器能打开网页，不一定说明 Node 子进程使用了相同代理。模板保留网络检测与探测脚本，核对当前用户已有的网络设置，而不是自动编造一个代理地址。

本地 readiness 请求应绕过系统代理，避免回环请求被送到外部代理。判断服务启动，还需要确认端口、进程与本项目归属；不能只看到一个 `node.exe` 就认定正确服务在运行。

遇到端口被占用，应另选本项目端口。停止脚本围绕当前运行项目，不应按进程名称停止其他人的服务。

## 常见失败怎样定位

| 现象 | 首先检查 |
| --- | --- |
| 浏览器正常，Node 请求失败 | 当前进程的网络设置、代理状态、证书与原生错误 |
| 授权页已确认，后台仍失败 | Token 交换结果和本项目认证保存状态 |
| 设备授权被拒绝 | 实际错误码与账号 / 地区 / 组织条件，不能统一归为网络 |
| 网关 ready，但模型不回答 | 可用模型、授权、额度与真实请求错误 |
| 登录完成却没有微信二维码 | 当前是否还停留在模型授权阶段 |
| 扫码后没有回复 | 微信通道、入站消息、模型与出站结果逐层核对 |
| 二维码过期 | 当前活跃配对进程与最新二维码，不能重复使用旧截图 |

详细处理见 [故障定位](references/troubleshooting.md)。日志可能包含私人消息，公开排错应只提供去除授权与正文后的错误摘要。

## 真正的收发验收应该做什么

建议至少进行两轮：第一轮发一个可识别的问题，在手机确认回复；第二轮引用上一轮内容，检查上下文是否按预期延续。结合通道入站、模型响应和出站结果，定位是否发生重复、超时或丢失。

本地自检、语法检查、服务 ready、手机收到一条消息和连续上下文往返，是不同的证据。只有实际执行了对应路径，才能记录那一层已经验证。

## 仓库与运行目录的区别

| 位置 | 内容 | 是否用于公开分享 |
| --- | --- | --- |
| 本仓库 `scripts/` | 项目生成入口 | 是 |
| 本仓库 `assets/project/` | 配置和运行脚本模板 | 是 |
| 本仓库 `references/` | 兼容、诊断、维护和验证说明 | 是 |
| 生成项目 `state/` | 认证、会话与个人状态 | 否 |
| 生成项目 `logs/` | 可能含私人消息的运行日志 | 否 |
| 生成项目其他运行目录 | 缓存、二维码与依赖 | 不作为安装方法包分享 |

分享方法时应分享这个模板仓库，不能把已登录的运行目录整个压缩上传。
